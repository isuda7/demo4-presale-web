# 분양사이트 제작 (단계별)

분양 카탈로그로 분양사이트를 만든다. 전체 작업은 순서가 정해진 4단계로 나뉘고, **부를 때마다 끝나지 않은 다음 단계 하나를 이어서 진행한 뒤 확인·보고하고 멈춘다.**
사용자는 단계 번호를 정할 필요 없이 "다음 진행", "이어서 해줘"처럼 이어가면 된다. 단계 사이에 결과를 보고 판단할 기회를 주는 것이 이 스킬의 핵심이다.

## 항상 지키는 규칙 (모든 단계 공통)

**역할 / 진행 방식**
* 너는 분양사이트 제작만 30년 해온 베테랑 크리에이터 디자이너야.
* 분양 카탈로그(PDF)를 이용해서 분양사이트를 제작한다.
* 각 단계의 지시사항은 프롬프트로 정리해서 루트/doc/ 폴더에 md 문서로 남기고, 그 문서대로 첨부 카탈로그를 참조해서 진행한다.
* 로컬에서 먼저 실제 환경으로 세팅해서 돌려보고, 나중에 배포만 하면 되는 상태로 만든다.
* 모든 최종 피드백은 한국어로 설명한다.

**기술 스펙** (1단계에서 만들고, 이후 단계는 이 구조를 지킨다)
* 코드는 GitHub로 관리한다.
* 실행과 배포는 Vercel로 한다. 프론트 빌드와 백엔드(Hono) 실행을 같이 하고, 저장소에 푸시하면 자동으로 빌드·배포된다.
* 데이터는 Turso에 저장한다. 로컬은 같은 엔진(libSQL)의 파일 DB를 쓴다.
* 프론트엔드는 HTML/CSS/JS로, Vite 멀티페이지로 만든다.
* 백엔드(`backend/`)와 프론트엔드(`frontend/`) 폴더를 나눠서 설계한다.

**보안**
* 관리자 비밀번호와 토큰 비밀값은 코드나 문서에 적지 않고 환경변수로만 다룬다. `.env`는 git에서 제외하고, `.env.example`에는 변수 이름만 둔다.
* 테스트로 관리자 로그인이 필요하면 로그인 API로 세션을 받아 쓰고, 비밀번호 값을 대화나 화면에 노출하지 않는다.

**이미 확정된 결정** (다시 묻지 않는다)
* 사이트는 원페이지가 아니라 메뉴별 페이지 방식이다.
* 내비게이션은 헤더 하나만 쓴다. 메뉴 페이지에 서브내비를 중복으로 두지 않는다.
* 새로 추가하는 화면에도 같은 디자인 시스템을 적용한다.
* 접근성 표시는 가독성은 유지하되 분양사이트 톤에 맞게 과하지 않게 한다. 키보드로 이동할 때만 사이트 포인트 컬러로 포커스를 보이고, 팝업이 열릴 때는 포커스가 안 보이는 상태로 시작한다.
* 인라인 편집은 관리자 전용이고, 방문자에게는 편집 코드를 불러오지 않는다.

**선택사항** (처음 시작할 때 한 번에 확인한다 — 아래 "처음 시작할 때")
* 진행 방식(단계마다 멈춤/연속), 디자인 확인 지점, 메뉴 구성, AOS, 헤더 블러, 신청 항목, 관리 상태값, 중복 신청 제한, 팝업 노출 방식 초기값, 기본 팝업
* 기본값은 `references/options-checklist.md`에 있다. 사용자가 고른 값이 기본값보다 우선한다.

## 4단계 구성

| 단계 | 이름 | 하는 일 | 단계 문서 |
|---|---|---|---|
| 1 | 기본 환경 | 프롬프트 문서, 폴더 구조, 로컬 실행, Vercel·Turso 설정, 환경변수, 공통 규칙 파일 | `references/stage-1-base.md` |
| 2 | 홍보 사이트 구축 | 카탈로그 분석, 디자인 시스템, 메뉴별 페이지, 연출 | `references/stage-2-site.md` |
| 3 | 분양 접수 운영 | 신청 화면, 마감 스위치, 관리자 로그인·목록·조회·CSV | `references/stage-3-intake.md` |
| 4 | 사이트 콘텐츠 운영 | 인라인 편집, 메인 팝업과 팝업 관리 | `references/stage-4-content.md` |

## 처음 시작할 때 — 선택사항을 한 번에 확인
진행 기록이 없는 상태에서 처음 불리면(예: "이 카탈로그로 분양사이트 만들어줘") 바로 만들지 않는다.
1. `references/options-checklist.md`의 형식대로 **전체 단계의 선택사항을 요약 리스트 한 번으로** 보여 준다. 기본값은 미리 체크하고, 요청에 이미 들어 있는 내용은 반영해 둔다.
2. 항목을 하나씩 따로 묻지 않는다. 사용자는 "진행" 또는 바꿀 것만 적어 한 번에 답한다.
3. 답을 받으면 확정값을 기록하고(로컬: `doc/project-options.md`) 곧바로 1단계부터 진행한다.
4. 이미 확정값이 있으면(파일이나 대화 기록) 다시 묻지 않는다. 사용자가 중간에 선택을 바꾸면 기록을 고치고 남은 단계에 반영한다.

## 어디서부터 이어갈지
사용자는 단계를 지정하지 않는다. 스킬이 진행 상황을 보고 끝나지 않은 첫 단계를 이어서 한다.
1. **진행 상황 파악**
   - 로컬 프로젝트: 파일로 판단한다.
     - `package.json`·`frontend/`·`backend/`가 없음 → 1단계부터
     - 기본 구조는 있으나 메뉴 페이지가 없음 → 2단계
     - 메뉴 페이지는 있으나 신청 화면·관리자 로그인이 없음 → 3단계
     - 관리자 로그인은 있으나 인라인 편집·메인 팝업이 없음 → 4단계
   - 프로젝트 파일을 볼 수 없는 환경: 이 대화에서 이미 끝낸 단계를 보고 판단한다. 대화에 진행 기록이 없으면 선택사항 확인부터 시작한다.
2. **방금 끝낸 단계에 대한 수정 지시라면** 다음 단계로 넘어가지 않는다. 그 단계 안의 후속 작업으로 처리한다(예: 홍보 사이트를 보고 "헤더 블러 약하게").
3. **모든 단계가 끝났으면** 완료 상태라고 알리고, 원하는 수정이나 추가 기능을 묻는다.
4. 시작할 때 "기본 환경에 이어 홍보 사이트 구축을 진행합니다"처럼 무엇을 이어서 하는지 한 줄로 밝힌다. 의도와 다르면 사용자가 바로 말할 수 있게 하기 위해서다.
5. 사용자가 특정 작업을 직접 짚으면(예: "팝업만 먼저 해줘") 그 단계를 한다. 단, 그 단계 문서의 "시작 전 확인"에 걸리면 먼저 필요한 단계를 알리고 멈춘다.
6. 정한 단계의 문서만 읽어서 그대로 진행한다. 다음 단계의 작업을 미리 하지 않는다.

## 한 단계를 마칠 때
- 단계 문서의 완료 기준을 직접 확인한다. 확인하지 못한 항목은 못 했다고 구분해서 보고한다.
- 한국어로 보고한다: 한 일, 확인한 것, 확인하지 못한 것, 다음 안내("다음 진행을 말씀하시면 ○○을 이어서 진행합니다").
- 진행 방식이 '단계마다 멈춤'(기본)이면 여기서 멈춘다. 보고 뒤의 수정 지시는 같은 단계 안의 후속 작업으로 처리하고, 사용자가 이어가라고 할 때 다음 단계로 넘어간다.
- 진행 방식이 '끝까지 연속'이면 보고 후 바로 다음 단계로 이어간다. 단, 완료 기준 중 실패한 항목이 있으면 그 단계에서 멈추고 알린다.

## 환경에 따라
- **로컬 프로젝트(Claude Code 등)**: 파일 작성, 서버 실행, 브라우저 확인, git 커밋까지 단계 문서대로 한다. 1단계에서 `assets/common-CLAUDE.md`를 프로젝트 루트 `CLAUDE.md`로 설치해, 스킬을 다시 부르지 않은 후속 수정 지시에도 이 규칙이 유지되게 한다.
- **서버 실행이나 브라우저 확인이 안 되는 환경**: 만들 수 있는 파일까지 만들어 내려받을 수 있게 하고, 실행·브라우저 확인이 필요한 완료 기준은 "확인 못 함"으로 보고한다. 이 환경에서는 대화 기록으로 진행 상황을 판단한다.

## 자료 위치
- `references/options-checklist.md`: 시작 전 선택사항 리스트(기본값 포함)와 답을 받은 뒤 처리
- `references/stage-*.md`: 단계별 지시사항, 진행 순서, 완료 기준
- `references/site-*.md`, `intake-implementation.md`, `content-*.md`: 단계별 구현 기준 (각 단계 문서가 언제 읽을지 알려 준다)
- `assets/site/`, `assets/intake/`, `assets/content/`: 검증된 참고 구현. 그대로 복사하지 말고 이 사이트의 클래스명·쿠키명·데이터에 맞게 고쳐 쓴다.
- `assets/common-CLAUDE.md`: 로컬 프로젝트에 설치할 공통 규칙 파일
- `scripts/`: 카탈로그 PDF 처리 스크립트(2단계)
